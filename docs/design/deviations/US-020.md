# Deviations — US-020 (M7 team mode: worktrees, shared task list, merge policy)

Against `docs/design/m6-m7-skills-agents-contract.md` §5 and §7, and plan AC-16. Recorded here rather than appended to the contract, per the lead's note about concurrent edits losing sections.

1. **`conflict` is the re-queued state, not a moment in passing.** The contract §5 sentence reads "task → `conflict` (retries+1) and re-queued", which could be read as `conflict` then immediately `queued`. AC-16 settles it: `snowpea team status` must show the task as `state:"conflict"` *with* `retries:n` while the worker redoes it. So a conflicted task sits in `conflict`, and `TeamStore.claim` treats `queued` and `conflict` as equally claimable (the `agent_n` predicate keeps it with the same worker). `queued → claimed → done → merged` is the happy path; `done → conflict → claimed → done → merged|failed` is the retry path.

2. **The retry counter reaches `team.max_conflict_retries`, it does not exceed it.** On a conflict the lead fails the task when `retries >= max_conflict_retries` and otherwise increments. With the default of 2 that is three merge attempts, two re-queues, and a `failed` row whose `retries` reads exactly `2` — which is what AC-16's "정확히 2회 재시도 후 failed" asserts. Incrementing first would have left `retries:3` on the failed row.

3. **Workers get an unregistered stand-in `Session`, not a second real session.** `SubagentManager` (US-019, read-only here) builds a child session from `parent.workdir`, `parent.mode`, `parent.provider` and `parent.backend`, and emits `subagent.*` on `parent.id`. `TeamManager._anchor` hands it a `Session` dataclass that is never registered with `SessionManager`: it carries the **lead's** id (so every `subagent.*` event still lands on the lead session, as §3 requires) and the **worktree's** path and backend (so the worker's real child session, tools and file writes are rooted in its own checkout). No change to `subagent.py` was needed.

4. **The worker's concurrency limit is the worker count.** The stand-in's `max_concurrent` is `n`, so `SubagentManager.semaphore_for` sizes the lead's semaphore to `n` for the duration of the run. Without this, `/team 5` would have been throttled to `agents.max_concurrent` (default 3).

5. **The team commits, the worker does not.** §5 says workers "commit on their branch". A worker subagent is told *not* to run git; `TeamManager._work` does `git add -A` and `git commit` itself once the subagent answers. A scripted model that forgets to commit would otherwise silently produce an empty merge, and the state machine would have no fact to act on. The worker's prompt says so explicitly.

6. **"Is there anything to merge?" is asked with `git merge-base --is-ancestor`, not with `git status`.** A re-queued worker that reproduces the same tree has nothing new to commit, but its branch is still unmerged and must go back to the merge loop so the conflict is counted. So after committing (or not), the lead asks whether the branch tip is already an ancestor of the base branch; if it is, the task becomes `merged` with a note saying nothing needed merging, otherwise it becomes `done` and queues for the merge loop.

7. **Git runs on the daemon host, not through the session's execution backend.** `agent/team.py::git` is a plain `asyncio.create_subprocess_exec`. Worktree creation, merges and cleanup are lead-side repository surgery, and `ExecutionBackend` has no worktree notion. A `docker`/`ssh` session therefore gets team mode against the daemon's own checkout; the worker *subagents* still run their tools on the session's backend (`SharedBackend`), which is what AC-18 constrains. Revisit when team mode is wanted on a remote backend.

8. **`team_tasks` / `team_messages` live in `agent/team_store.py`, not in `session/store.py`.** Same reasoning US-017 used for `marketplaces.json`: `session/store.py` was being edited by other stories, and a standalone module with its own connection to the same `$SNOWPEA_HOME/state.db` keeps the merge surface at zero. The schema is created on first use. A third table, `teams`, holds the run header (session, workdir, repo, task, worker count, state) so `team.status` can answer after a restart.

9. **Protocol extensions (all additive, all defaulted).**
   - `TeamTaskState` is a new alias — `pending|queued|claimed|running|done|conflict|merged|failed`, a strict superset of `TaskState` — and `TeamTask.status` / `TeamTaskUpdate.status` use it. Nothing else emitted a team task state, so no existing payload changes shape.
   - `TeamTaskUpdate` gained `agentN` and `retries`, which §5 names in the event and the model did not carry.
   - `TeamTask` gained `agentN`, `retries`, `branch`, `note`, `dependsOn`, `conflictHunks` and `conflictSummary`; `TeamStatusResult` gained `workers`, `task` and `worktrees`. AC-16 asks `team status` for the retry count, the attached hunks and the worktree list.
   - `TeamStatusParams.teamId` became optional (default `""`), because the contract's CLI is `snowpea team status [teamId]` and the daemon has to be able to answer for the most recent run.
   - `team.start` and `team.status` joined `IMPLEMENTED_METHODS`. `sdk/src/protocol.ts` and `docs/protocol.md` were regenerated; `gen_protocol.py --check` is clean.

10. **`team.start` answers before the run finishes; `/team` waits for it.** The RPC returns the `teamId` as soon as the board is written and the worktrees exist, so a client can poll `team.status` and watch `team.task.update`. The slash command awaits `TeamManager.wait(teamId)` so that `turn.done{complete}` really means the merges are done and the worktrees are gone.

11. **A task whose dependency failed fails with it.** §5 says a worker claims a task "whose deps are merged". If a dependency ends `failed`, that condition can never hold and the worker loop would spin forever, so the dependent task is marked `failed` with the note `blocked: a task it depends on failed`. The alternative — leaving it `queued` — would hang the team, which AC-16 explicitly forbids ("팀 전체가 멈추지 않는다").

12. **`snowpea team` is no longer a placeholder, and `PLACEHOLDER_SUBCOMMANDS` is now empty.** `team` was the last entry (US-017 had already implemented `skill`, and `service` landed alongside). The tuple and the `placeholder()` helper are kept so the next unimplemented subcommand has somewhere to go. `cli/commands.py` also gained `_call`, a params-carrying sibling of the existing `_lookup`, because `team.status` is the first session-less subcommand that sends arguments.

13. **Worker prompts, and the hunks in them.** A re-queued worker's brief includes the conflicted diff verbatim (capped at 4000 characters) under an instruction to redo the work so it applies on top of what other agents already merged. The hunks are captured with `git diff --name-only --diff-filter=U` plus `git diff --diff-filter=U` *before* `git merge --abort`, and fall back to the merge command's own output when the diff is empty (a rename/delete conflict, say).

14. **Test fixtures.** `tests/fixtures/providers/fake/team.json` drives the three-module run; `team_conflict.json` drives the always-conflicting one, where the second worker rewrites the same single line of `shared.txt` that the first worker already merged and a `delaySec` guarantees it is merged second. Both scripts match on `your task <id>:`, a string that cannot appear inside a conflict diff, so a re-queued worker keeps matching its own step rather than another task's.
