# Deviations — US-019 (M7 서브에이전트 + 내장 워크플로 + 번들 스킬)

`docs/design/m6-m7-skills-agents-contract.md` §3·§4·§7, plan AC-03 / AC-04 / AC-15b,
`docs/omc-porting-map.md` 기준. 계약서 본문을 고치지 않고 여기에 적는 것은 US-013 이후의 관례를
따른 것이다.

## 프로토콜

1. **`subagent.*` 페이로드에 필드를 더했다(제거 없음).** M1 스텁은
   `SubagentUpdate{agentId, status, text}` / `SubagentDone{agentId, ok, result}`였는데 계약 §3은
   `update{..., lastText?}` / `done{..., status, summary, usage}`를 요구한다. 기존 필드를 지우면
   M1 스키마를 읽은 클라이언트가 깨지므로 **양쪽 다** 채운다: `text`와 `lastText`는 같은 문자열,
   `ok`/`result`는 `status`/`summary`와 같은 뜻이다. TUI 리듀서도 둘 다 읽는다
   (`tui/test/store.test.ts`의 "reads the older ok/result spelling").
   새로 추가한 것: `SubagentStatus = "queued"|"running"|"done"|"error"` 리터럴,
   `SubagentUsage{inputTokens, outputTokens}`, spawn/update/done 공통의 `sessionId`·`name`,
   `SubagentSpawn.status`.
2. **`AgentInfo`에 서브에이전트용 선택 필드 5개를 더했다.** `status`, `task`, `agentId`,
   `sessionId`, `parentSessionId` — 전부 `None` 기본값이라 `kind:"definition"`·`kind:"named"`
   행의 모양은 그대로다. `snowpea agents --json`이 AC-04의 "running 2개 이상"을 판정하려면
   상태와 부모 세션이 한 행에 있어야 한다.
3. **`agent.spawn`의 `sessionId`를 SDK에서 노출했다.** 프로토콜 `AgentSpawnParams`에는 원래부터
   있었지만 `sdk/src/agents.ts`의 `spawnAgent(client, name, task)`가 넘기지 않아 데몬이 "열려 있는
   유일한 세션"으로 추측해야 했다. 선택 인자 `sessionId?`를 마지막에 추가했다(기존 호출부는 그대로
   동작).

`uv run python scripts/gen_protocol.py`는 같은 변경에서 돌렸고 `--check`가 통과한다.

## 세션과 에이전트 루프

4. **`Session`에 `parent_session_id`와 `system_prompt`가 생겼다.** 계약 §3이 자식 세션에
   `parent_session_id`를 요구하고, 에이전트 정의의 본문(시스템 프롬프트)을 실제로 적용하려면
   `agent/agent.py`의 `BASE_PROMPT`를 갈아끼울 자리가 필요하다. `build_system_prompt`는
   `getattr(session, "system_prompt", None) or BASE_PROMPT`로 읽으므로 두 필드를 모르는 코드는
   영향을 받지 않는다.
5. **자식 세션은 부모의 백엔드를 `SharedBackend` 프록시로 공유한다.** 계약은 "same backend"라고만
   적었는데, 그대로 같은 객체를 물려주면 자식이 닫힐 때 `SessionManager.close()`가
   `backend.close()`를 불러 **부모가 쓰는 docker 컨테이너/ssh 연결이 끊긴다**. 프록시는
   `__getattr__`로 전부 위임하고 `close()`만 no-op이다. 결과적으로 `/backend docker`는 계약대로
   트리 전체를 움직이면서(AC-18) 자식의 수명은 부모와 분리된다.
6. **부모가 자식을 보는 경로는 `EventHub.subscribe(watcher, child_id)`다.** 토큰 사용량과 마지막
   텍스트를 모으려고 `agent/loop.py`에 훅을 넣는 대신, 자식 세션을 구독하는 가짜 커넥션
   (`_ChildWatcher`)을 붙였다. US-017이 `loop.py`를 동시에 고치고 있어서 그 파일을 건드리지 않으려는
   이유도 있지만, 더 중요한 것은 **에이전트 루프가 서브에이전트를 전혀 모르는 상태로 남는다**는
   점이다. 워처는 자식의 `usage`를 누적하고 `message.done`·`tool.call`을 부모의
   `subagent.update`로 다시 발행한다.

## 워크플로

7. **`/ralph`의 검증은 셸 툴이 아니라 백엔드 직접 호출이다.** 스토리의 `verify` 명령은
   `backend.run(...)`으로 돌린다. `shell` **툴**로 돌리면 `accept` 모드에서 승인 프롬프트가 뜨고,
   무인 ralph 실행이 사람을 기다리며 멈춘다. 검증은 모델이 고른 행동이 아니라 워크플로가 계약상
   반드시 해야 하는 일이므로 정책 게이트 밖에 둔다. 자식 에이전트가 하는 편집·실행은 전부
   정상적인 권한 경로를 지난다.
8. **`ralph.max_iterations` 설정을 새로 만들었다.** 계약 §4가 기본값 10을 요구하는데
   `config/settings.py`에 자리가 없었다. `RalphSettings{max_iterations: int = 10}`를 추가했다.
   프로젝트 단위 오버라이드는 아직 없다(`agents.max_concurrent`과 달리 `ProjectSettings`에
   대응 필드를 두지 않았다) — 필요해지면 그때 더한다.
9. **리뷰어 서브에이전트의 `agent="architect"`는 조건부다.** 계약 §4는 "reviewer subagent
   (architect)"라고 적었지만 갓 클론한 저장소에는 `agents/architect.md`가 없다. 정의가 있으면
   이름으로 띄우고, 없으면 이름 없이 세션 설정 그대로 리뷰를 돌린다. 정의가 없다고 ralph가
   실패하지는 않는다.
10. **스토리 배치 규칙이 계약보다 조금 더 구체적이다.** "≥2 concurrent when independent"를
    구현하려면 "independent"의 정의가 필요했다. `depends_on`이 전부 통과했고
    `independent != false`인 스토리를 `agents.max_concurrent`개까지 묶는다. `independent: false`인
    스토리는 혼자 돈다. 첫 배치 대상이 `independent: false`면 그 하나만 돈다.
11. **`/deepinit`은 최상위 디렉터리 + 루트에서 멈춘다.** OMC 원본은 트리 전 깊이에 `AGENTS.md`를
    쓴다. 파일 수 임계값(2개 미만이면 생략)과 스킵 목록으로 범위를 줄였고, 하위 트리를 문서화하려면
    `/deepinit <path>`로 다시 부른다. 모듈 docstring 하단의 "Differences from the OMC original"에
    같은 내용이 있다.

## 번들 스킬

12. **번들 SKILL.md 3종은 OMC 원문 복사가 아니라 snowpea용 재작성이다.** 계약 §4의 "original texts
    written for snowpea"를 따랐다. `docs/omc-porting-map.md` §2는 "prompt text we keep verbatim"이라고
    적혀 있어 두 문서가 서로 다르게 읽힐 수 있는데, 원문을 그대로 가져오면 `state_write`,
    `AskUserQuestion`, `Task`, `.omc/specs/`, `settings.json`의 `omc.deepInterview.ambiguityThreshold`처럼
    **snowpea에 존재하지 않는 도구와 경로를 지시하는 문장**이 그대로 남는다. 대신 방법론을 보존하고
    각 파일 하단에 "Differences from OMC" 절로 무엇이 왜 달라졌는지 전부 열거했다(포팅 맵 §3의
    체크리스트 2번).
    - `deep-interview`: 임계값 0.2 고정, Phase 0 없음, 상태 파일/재개 없음, `explore` 서브에이전트 없음.
    - `deep-research`: OMC에 같은 이름의 스킬이 없어 `external-context`(팬아웃) +
      `autoresearch`(증거 규율)에서 합성했다. 미션 루프·평가자 계약·cron은 가져오지 않았다.
    - `ralplan`: `/plan --consensus` 별칭이 아니라 루프를 직접 적었다. 게이트는 리디렉션이 아니라
      권고이고, `--interactive`/`--deliberate`/codex 라우팅 플래그는 없다.
13. **`commands/builtin_skills.py`라는 폴백 등록 경로를 하나 더 뒀다.** 계약 §4는 세 스킬을
    US-017의 로더가 `source=builtin`으로 읽는다고 정한다. 로더는 실제로 들어와 있고 그 경로가
    정상 경로다. 다만 `/help`가 9개를 보이는 것(AC-03)이 로더의 존재에 의존하면
    `SNOWPEA_DISABLE_SKILLS`나 로더 장애에서 명령이 통째로 사라진다. 그래서
    `register_builtin_commands`가 같은 파일들을 직접 파싱해 먼저 등록하고, 로더가 나중에 같은
    이름으로 덮어쓴다(레지스트리는 이름 기준 last-write-wins). 프런트매터 파서는 M6 패키지에
    의존하지 않도록 `agent/definition.py`의 `split_frontmatter`를 쓴다.
    → `tests/test_ralph_e2e.py::test_help_lists_the_nine_commands`는 xfail이 아니라 그냥 통과한다.

## 그 밖에

14. **`delegate_task` 스텁을 `tools/stubs.py`에서 지웠다.** 이름·카테고리(`delegate`)·권한 태그
    (`exec`)·입력 스키마의 `task`/`agent`는 그대로 두고 `tools/delegate.py`의 실물로 바꿨다.
    `tools` (배열)와 `timeout` (초)을 스키마에 추가했다. `tool.list`를 M1에 읽은 클라이언트 입장에서는
    같은 툴이 `inactive` → `active`로 바뀐 것으로 보인다.
15. **`SubagentManager`는 `Core`의 필드가 아니라 `get_manager(core)`가 붙이는 지연 속성이다**
    (`core._subagents`). `server/app_server.py`의 `Core` 데이터클래스는 US-015·US-016·US-021이
    동시에 편집 중이라 필드 추가를 피했다. 동작은 같고, 나중에 정식 필드로 승격해도 호출부는
    `get_manager(core)` 하나뿐이다.
16. **`agent.list`는 끝난 자식을 빼고 보여준다.** 계약 §3이 "running/queued subagents"라고 적었으므로
    `queued`·`running`만 나간다. 끝난 기록은 매니저 안에 최대 200건 남아 있어
    `manager.records()`로 볼 수 있다(`snowpea agents`가 나중에 히스토리를 보여주고 싶을 때를 위해).
17. **`snowpea agents`가 `PLACEHOLDER_SUBCOMMANDS`에서 빠졌다.** `service`와 `team`은 그대로 남는다
    (`team`은 US-020).
