# Deviations — US-014 (M5 long-term memory)

Against `docs/design/m5-memory-scheduler-gateway-contract.md` §1 and §5. Everything in §1 is implemented as written except where noted.

1. **The tools live in `memory/tools.py`, not `tools/memory.py`.** §1 says to replace the US-009 inactive stubs in `tools/memory.py`. US-009 finished (its deviations file landed) without creating that module: the `memory_write` / `memory_search` placeholders stayed in `tools/stubs.py`, which US-009 owns. Rather than edit another story's file, the real tools are `memory/tools.py` and `register_memory_tools(registry)` re-registers them under the same names. `ToolRegistry.register` is keyed by name, so the active tools replace the inactive stubs; `wire_core` calls it (through `memory.wire_memory`) right after `register_builtin_tools`. Tool names, categories and descriptions are unchanged, so `tool.list` looks the same apart from `state: "active"`.

2. **FTS5 queries are built from the query's own trigrams.** The `trigram` tokenizer indexes every 3-gram of a document, but it also tokenizes the *query*, so `MATCH '내 배포 대상이 뭐였지?'` is a phrase search that matches nothing, and a term shorter than three characters is a syntax error. `memory/store.py` therefore ORs the query's deduplicated overlapping 3-grams (capped at `MAX_QUERY_TRIGRAMS = 48`), which behaves as a substring search and lets bm25 rank the row sharing the most of them first. A query too short for one trigram (`"배포"`) falls back to `LIKE '%…%'` inside the namespace, which is what the user meant anyway.

3. **`MemoryStore` opens its own connection to `state.db`.** `session/store.py` keeps a private connection behind a lock and exposes no way to borrow it; adding one would mean editing a file three other stories are touching. Memory opens a second connection to the same file with `busy_timeout = 5000`. `Daemon.stop` closes it beside the session store.

4. **`Core` gained a `memory` field and `Session` a `memory_namespace` field.** Both are one additive line with a default, so no existing call site changed. `memory_namespace` defaults to `"default"`; M7's named agents set it to `"agent:<name>"`. `memory.retrieval.namespace_of` reads it with `getattr`, so a session object that predates the field still works.

5. **`auto_remember_patterns` defaults live in `config/settings.py`.** They are configuration, and putting them in `memory/retrieval.py` would have made `settings` import `memory` while `memory` imports `settings`. `memory.retrieval` re-exports `DEFAULT_REMEMBER_PATTERNS` so the name is still reachable from the memory package.

6. **`memory.write` / `memory.search` take an optional `namespace`.** §1 marks it optional; `MemorySearchParams` and `MemoryWriteParams` gained `namespace: str | None = None` (default `"default"`) and `sdk/src/protocol.ts` plus `docs/protocol.md` were regenerated in the same change. The RPC pair carries no session id, so it cannot infer a namespace from one. `PROTOCOL_VERSION` did not move: the fields are optional and additive.

7. **The retrieval hook runs once per turn, not once per provider round.** §1 says "before each turn". Recall is keyed on the user's message, which does not change while the model is calling tools, so `agent/loop.py` builds the block once before the round loop and passes it to `build_messages`. This also keeps the system prompt stable across a turn, which matters for prompt caching.

8. **Recall and the nudge never fail a turn.** Both helpers in `memory/__init__.py` catch and log everything: a broken memory database must not cost the user their answer. The nudge also skips a fact whose exact text is already stored in that namespace, so repeating "기억해: …" does not accumulate duplicates.

9. **`UserProfile` is implemented but nothing writes to it yet.** §1 describes it as updated by the agent via `memory_write(tags=["profile:<key>"])`, which the tool already supports; `UserProfile.set/get/all/forget` is the typed view over those tagged rows for M7 to build on.

10. **Tests use a recording provider rather than a scripted one.** §5 suggests a fake-provider script whose step matches the injected memory text. `FakeProvider` only matches on the last *user* message and its replies are static, so it can neither see the system prompt nor echo a freshly generated `[mem:<id>]`. `tests/test_memory_recall.py` defines a small `RecordingProvider` that keeps every system prompt and answers by quoting the injected memory with its real id, and installs it on `core.providers.get`. The assertions are therefore about the actual system prompt the model received.
