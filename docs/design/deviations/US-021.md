# Deviations — US-021 (M7 이름 있는 영속 에이전트)

`docs/design/m6-m7-skills-agents-contract.md` §6(+§2), `docs/design/m5-memory-scheduler-gateway-contract.md`
§1·§3, plan AC-17 기준. 계약서 본문 대신 여기에 적는 관례는 US-013 이후와 동일하다.

1. **게이트웨이 바인딩의 `target`에 `session`을 같이 싣는다.** 계약 §6은 바인딩 대상이
   `{"agent": name}`이라고만 적는데, `gateway/router.py`의 `_create_session()`은 `agent` 키만 보면
   대화(채널)마다 **새 세션**을 연다 — 이름 에이전트의 영속 세션이 아니라. 라우터를 고치는
   대신(US-016 파일이고 다른 스토리가 건드릴 이유가 없다) `NamedAgentRegistry.bind_channel()`이
   `{"agent": <name>, "session": <그 에이전트의 세션 id>}`로 바인딩한다. `Binding.describe_target()`이
   `agent`를 먼저 보므로 `gateway.list`에는 계약대로 `agent:<name>`으로 보이고, 세션 id는 재시작을
   견디므로(아래 2번) 복원된 바인딩도 그대로 동작한다. 라우터는 이름 에이전트의 존재를 모른다.

2. **`SessionManager.create()`에 선택 인자 `session_id`가 생겼다.** AC-17이 "재시작 후 같은 세션"을
   요구하는데 기존 API는 항상 새 uuid를 만든다. 기본값 `None`이라 기존 호출은 전부 그대로이고,
   `named_agents.session_id`로 세션을 다시 여는 경로에서만 쓴다(`sessions` 행은 `INSERT OR REPLACE`).

3. **복원 순서: 이름 에이전트가 게이트웨이보다 먼저다.** `Daemon.start`에서
   `core.named_agents.restore()`를 `core.gateway.restore()` **앞**에 부른다. 그래야 1번의
   `session` 대상이 이미 열려 있어 바인딩 복원이 `GatewayError`로 떨어지지 않는다. 계약 §6은
   "레지스트리가 세션·바인딩·잡을 다시 붙인다"고 적었지만, 바인딩 재부착 자체는 이미 있는
   `GatewayRouter.restore()`가 하고 레지스트리는 그 전제(세션)를 만든다. 잡은 `jobs` 테이블에서
   스케줄러가 스스로 복원하므로, 레지스트리는 `agent` 컬럼으로 잡 id만 다시 읽어
   `schedule_ids`를 갱신한다(= 파생 데이터, 진실은 `jobs` 테이블).

4. **`named_agents` 테이블은 자체 SQLite 커넥션을 쓴다.** US-016의 `BindingStore`와 같은 이유다:
   같은 `state.db` 파일이지만 세션 스토어 배선과 무관하게 복원할 수 있고, 다른 스토리가 편집
   중인 파일(`session/store.py`)에 메서드를 더하지 않는다.

5. **`agent.create`에 `named`·`name`, `agent.bindChannel`에 `credentialsRef`를 **추가**했다.**
   전부 선택 필드라 기존 클라이언트는 영향이 없다. `credentialsRef`가 필요한 이유: 계약의
   `bindChannel(name, channel)`에는 자격증명 참조가 없는데 `GatewayRouter.bind()`는 반드시 하나를
   받는다. 생략하면 플랫폼 이름(`telegram:123` → `"telegram"`)을 참조로 쓴다. `AgentInfo`에는
   `namespace`·`channels`·`bindings`·`jobs`를 추가하고 기존 단수 `channel`에는 첫 채널을 채운다.
   `IMPLEMENTED_METHODS`에 `agent.bindChannel`·`agent.delete`를 넣고 같은 변경에서
   `scripts/gen_protocol.py`를 돌렸다.

6. **에이전트 세션의 workdir는 "정의 파일이 속한 프로젝트", 없으면 `$SNOWPEA_HOME`이다.**
   스토리 설명은 "settings 기본값 또는 정의 디렉터리"라고 했지만 `settings.json`에는 기본 작업
   디렉터리 항목이 없다. 그래서 `<project>/.snowpea/agents/<name>.md` → `<project>`로 거슬러
   올라가고, 정의가 없거나 경로가 관례를 벗어나면 홈을 쓴다.

7. **정의의 `tools`(allowed-tools)는 세션에 걸지 않았다.** `Session.allowed_tools`는 "이번 턴만"
   제한하는 스킬 명령 전용 필드라 영속 세션에 상시로 걸면 의미가 달라진다. 정의의 `prompt`는
   `Session.system_prompt`로, `permission`은 `plan|accept|auto`일 때만 세션 모드로 반영한다
   (`inherit`/빈 값이면 프로젝트 기본 모드).

8. **스케줄러 훅은 `_execute()` 안의 3줄이다.** `job.agent`가 이름 에이전트를 가리키면
   `named.session_for_job()`이 그 세션을 돌려주고, 스케줄러는 새 세션을 만들지 않으며 실행이
   끝나도 **닫지 않는다**(빌려 쓴 세션이다). 가리키지 않으면 기존 동작 그대로다.

9. **RPC 핸들러 본문은 `agent/named.py`에 있고 `server/agent_handlers.py`에는 등록 2줄과
   `agent.list`의 named 항목 추가만 들어갔다.** US-019가 같은 파일을 동시에 편집하기 때문이다.
   `agent.list`는 정의(`kind:"definition"`)와 영속 인스턴스(`kind:"named"`)를 **둘 다** 반환한다 —
   같은 이름이 두 줄로 보이지만 계약 §3이 `kind`로 구분하라고 적었고, CLI 표시는 US-019 소관이다.
