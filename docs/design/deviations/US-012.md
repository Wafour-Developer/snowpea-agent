# Deviations — US-012 (M3 setup wizard: Quick / Full / Blank)

Against `docs/design/m3-providers-setup-contract.md` §5 and plan §4 M3 / AC-02 /
AC-02b. Recorded here rather than appended to the contract, per the deviations
README.

Implemented: `setup/catalog.py`, `setup/state.py`, `setup/detect.py`,
`setup/ui.py`, `setup/wizard.py`, `setup/screens/{providers,search,browser,tools,gateway,done}.py`,
the `snowpea setup` subcommand in `cli/commands.py`, two additive fields in
`config/settings.py`, and `tests/test_setup_wizard.py`.

## Deviations

1. **The search catalog is re-sorted into the three AC-02b buckets, not shown in
   raw registry order.** US-009's `PROVIDER_ORDER` puts `brave_free`
   (`free` / `key required`) second, ahead of four `free` / `no key` providers,
   so "registry order" and "free·no-key first" cannot both hold literally.
   `search_catalog()` does a *stable* sort by bucket — free·no-key, then
   free·key/self-hosted, then paid — which keeps the registry's relative order
   inside each bucket and satisfies AC-02b. The resulting head is
   `ddgs, exa_free, keenable_free, parallel_free, brave_free, tavily, searxng,
   firecrawl_selfhost, …`. `assert_free_first()` enforces the invariant and
   every builder returns through it, so a future provider with bad tags fails
   loudly rather than silently reordering the screen.

2. **`CatalogItem` gained a `tags` property.** §5 lists the fields
   (`id, label, tier, key, default, description, active`); `tags` is derived
   (`("free · no key", "active")`) so screens and tests never re-format tier and
   key by hand.

3. **`WizardState` lives in `setup/state.py`, a file §5 does not name.** The
   screens are pure `build`/`apply` pairs, so the thing they fold answers into
   has to exist outside both `wizard.py` (which imports the screens) and
   `screens/` (which must not import the wizard). `state.py` also owns
   `write()`, the single place that turns answers into `settings.json`.

4. **Media categories are `media-image` / `media-video` / `media-tts`.** §5
   writes them as "media(image/video/tts)". The tool registry's `category`
   field for those tools is just `media`, so the wizard needs three separate
   ids to toggle them independently; the shared `media-` prefix keeps the
   grouping visible.

5. **`tools.enabled_categories` defaults to `[]`, not to the default-on set.**
   Putting the catalog's default list in `config/settings.py` would make
   `settings.py` import `setup/catalog.py`, which imports the provider
   registries — a cycle risk for a module nearly everything imports. Empty
   means "nothing chosen yet"; readers fall back to
   `setup.catalog.default_enabled_categories()`. Every wizard run writes the
   explicit list, so AC-02b's "default ON set is recorded" holds.

6. **`settings.gateway` is `dict[str, dict[str, Any]]`, not a typed model.**
   The gateway story has not fixed the per-vendor shape yet; the wizard writes
   `{"telegram": {"enabled": true, "token": "..."}}` and disabled gateways are
   dropped rather than stored as `enabled: false`, so AC-02b's "gateway empty"
   is literal.

7. **A flag *answers* its screen instead of pre-filling it.** `snowpea setup
   --full --search-provider tavily` shows five screens, not six. This is what
   makes the flags a real non-interactive path rather than a default the screen
   then re-asks. `SetupResult.screens_shown` / `screens_answered` report which
   was which.

8. **Non-interactive is detected once, at the top of the run.** §5 says every
   screen has a CLI flag; it does not say what an unanswered screen does when
   there is no TTY. `ui.ask()` returns `Screen.default_choice` — the current
   selection, else the ★ default, else Skip — so a piped `--full` run is exactly
   the "all Skip" path AC-02b tests. `SNOWPEA_SETUP_NONINTERACTIVE=1` forces it.

9. **`--login` decides the unsupported case locally, then delegates.**
   `setup --login <vendor>` calls `providers/auth_web.method_for()` first: the
   nine API-key-only vendors (and unknown ids) print
   `error{code:"login_unsupported"}` plus the `--vendor/--key` hint and exit 2
   **without starting a daemon**. `openai` and `openrouter` fall through to
   `cli_commands.provider_login()`, i.e. the identical RPC path as `snowpea
   provider login`. Doing the check locally is what lets AC-02's control case be
   tested offline.

10. **The interactive list is hand-rolled on `rich` + `termios`.** `rich` has no
    list picker, so `ui.read_key()` puts the tty in raw mode for one keypress and
    `ui.ask()` redraws the whole screen per key. Single-select rows are
    `(●)`/`(○)` with ↑↓/Enter, multi-select `[✓]`/`[ ]` with Space, and Enter on
    `Skip — keep defaults` returns the defaults. `ui.render_lines()` renders a
    screen to plain text so the layout is testable without a terminal.

11. **The providers screen asks for the API key after the list, not as a row.**
    A key is free text, not a selectable item, so it is a separate
    `getpass` prompt that only runs interactively; an empty answer means "use
    the environment variable", which the registry already resolves.
    `setup/detect.py` surfaces the detected variable as a hint line above the
    list, and never copies a detected key into `settings.json`.

12. **`setup/__init__.py` does not re-export the `detect` function**, only
    `Detected`. Exporting it would shadow the `snowpea_core.setup.detect`
    submodule for `from snowpea_core.setup import detect`.

13. **`server/protocol.py` was not touched.** The wizard writes `settings.json`
    directly through `config/settings.py` and reuses
    `ProviderRegistry.configure()` for the provider block, so no new RPC and no
    protocol regeneration were needed.

## Not done here

* Importing an existing `~/.hermes/config.yaml` or Claude Code config.
  `detect.py` reports that one exists (a hint line); parsing it is a later story.
* `gateway/` itself. The wizard records tokens; nothing binds them yet.
* Wiring `tools.enabled_categories` into the tool registry's `state`. The
  wizard writes the field; US-009 owns `tools/registry.py`.
