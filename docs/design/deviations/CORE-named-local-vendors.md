# Deviations — named local vendors (several OpenAI-compatible servers)

Against `docs/design/m3-providers-setup-contract.md` §1–§3 and §5. Recorded here rather than appended to the contract, per the deviations-log convention. The contract itself carries a short note at §1 pointing at this mechanism.

1. **A twelfth vendor is not added; the vendor set becomes open at the edges.** `PRESETS` still holds exactly the eleven ids the contract fixes. What changed is that `PRESETS` is no longer the whole set of vendors: any key under `settings.providers` whose block carries `"preset": "local"` is a local-style vendor synthesized on the fly by `presets.synthesize_local_preset()`. Everything that used to branch on `vendor == "local"` now tests `VendorPreset.local_style` (`registry.is_local_style()`), so keyless auth, `/v1/models` discovery, the Ollama `/api/tags` fallback, placeholder-model resolution and live context-window probing reach a named server unchanged.

2. **`"openai-compatible"` is accepted as an alias of `"local"` in the `preset` field.** "local" reads oddly for a server on another host, and a user hand-editing `settings.json` writes what the row is, not where it runs. Both spellings mean the same thing; the wizard and the CLI always write `"local"`.

3. **`provider.remove` is a new RPC method.** The contract has no way to forget a provider: `provider.configure` merges, and a patch of nothing but `None` clears fields rather than the block. `snowpea provider remove <name>` needs one, and a removal has to take the model profiles and agent assignments that named the vendor with it, or the next prompt fails on a profile pointing at a server that no longer exists. `ProviderRegistry.remove()` is where that cleanup lives; the wizard's own removal path (`WizardState.remove_provider`) mirrors it on the pre-write state.

4. **`ProviderInfo` gained `preset` and `custom`.** Additive, so existing consumers are unaffected. `preset` is `"local"` for the built-in local vendor and every named server, and the vendor's own id otherwise; `custom` is true only for a name the user added. Without them a surface cannot tell which rows it may offer to remove.

5. **The `local` preset's label changed to "Local / OpenAI-compatible servers".** The old label ("OpenAI-compatible local (vLLM / Ollama / LM Studio)") described one server; the row now opens a list of them. `docs/design/deviations/US-023.md` §8 quotes the old label as the then-current `provider.list` output and is left as the historical record. The vendor tables in `docs/manual/{en,ko,ja,zh-CN}/setup.md` were updated.

6. **`variant` accepts `generic` in a settings block, but the wizard menu still offers three.** A named server may declare `"variant": "generic"` — a plain OpenAI-compatible server with no vendor quirk and no default port to guess — and `snowpea provider add-local --type generic` writes it. The interactive server-type menu still lists vLLM, Ollama and LM Studio only: those are the three whose default `base_url` the wizard can suggest, and a fourth row offering no suggestion would be a question with no answer. `LOCAL_VARIANTS` is unchanged; `LOCAL_VARIANT_IDS` is the wider accepted set.

7. **Add and remove are TTY-only in the wizard; scripts use the CLI.** Off a TTY `_menu_pick` returns `None` and the local flow configures whichever server is already selected — exactly the single-server behaviour that scripted `snowpea setup` runs have always had. Inventing a server name from a scripted answer stream would change what an existing non-interactive run writes. `snowpea provider add-local` / `remove` and `snowpea setup --vendor <name> --base-url <url>` are the scriptable routes.

8. **`--vendor <unknown-name>` is accepted only with `--base-url`.** A name nothing knows is a new OpenAI-compatible server when the same invocation says where it lives, and a typo otherwise. `snowpea setup --vendor antropic` still fails with "unknown vendor" as it did.

9. **A bare named server resolves as a model reference.** `config/model_routing.resolve_reference` accepted a bare vendor name only when it was in `PRESETS`; it now also accepts a configured local-style name, so `hon2` alone routes to that server and lets the registry pick the model, the way `local` alone always has. `hon2:flash-next-mtp` needed no change — it already went through the `vendor:model` branch.

10. **`compose.vendor_class_for` gained a `local_style` keyword.** A named server's id tells the prompt builder nothing, but it is running the same class of small model as the built-in `local` vendor and needs the same tool-use enforcement. `agent.build_system_prompt` passes the registry's answer; a caller without a `Core` gets the old "openai-family" default.

11. **`ProviderRegistry.configure` validates names it did not know before.** A key that is not a preset id is refused unless the merged block declares `preset: local` *and* the name matches `^[a-z][a-z0-9_-]{0,31}$` and does not shadow a preset id. That is stricter than the previous behaviour for built-in ids (unchanged) and looser for everything else, which previously could not be configured at all. A malformed key already in `settings.json` is skipped with a warning by `local_vendor_ids` rather than raising, so one hand-edited typo cannot stop the daemon from starting.
