# Deviations — US-016 (M5 게이트웨이 + 무인 승인 공유 큐)

`docs/design/m5-memory-scheduler-gateway-contract.md` §3·§4·§5, plan §3.1 gateway / §6 risk 4,
AC-09 / AC-17 / AC-20 기준. US-013과 같은 이유로 계약서 본문이 아니라 여기에 적는다.

1. **`gateway.bind`의 `target`이 문자열에서 객체로 바뀌었다.** M1 스텁 프로토콜은
   `target: str`("채널/방/챗 id")였는데, 계약 §3의 `bind(platform, credentials_ref, target)`은
   `{"agent": name} | {"session": id} | {"new_session": {workdir, mode}}`를 받는다. 라우팅 대상과
   대화 채널은 다른 축이라 `target: dict[str, Any]`로 바꾸고, 채널 제한은 새 선택 필드
   `channelId`로, 승인 응답을 허용할 사용자는 `userId`로 분리했다. `gateway.*`는 M1에서 미구현
   (`IMPLEMENTED_METHODS` 밖)이었으므로 깨질 클라이언트가 없다. `GatewayBinding` 결과에는
   `credentialsRef`·`channelId`·`userId`를 **추가**했고 `target`은 `agent:ops` 같은 사람이 읽는
   요약 문자열로 남겼다.
2. **`approval.pending` 알림이 새로 생겼다.** 계약 §4가 "`approval.request`를 알림으로
   브로드캐스트"라고 적었지만 `approval.request`는 이미 s2c **요청**(응답을 기다리는 호출)이라
   같은 이름을 알림으로 재사용하면 디스패치가 모호해진다. `EVENTS`에 `approval.pending
   {request: ApprovalRequest}`를 추가하고 `gen_protocol.py`를 같은 변경에서 돌렸다.
3. **`approval.list`는 이제 무인 요청만 돌려준다.** AC-20 마지막 문장("대화형 요청은 공유 큐에
   보이지 않는다")을 만족시키려면 필터가 필요한데, `approval.list` 핸들러는 US-014가 동시에
   편집 중인 `session_handlers.py`에 있다. 그래서 필터를 `ApprovalQueue.list(session_id, conn=None)`
   쪽에 넣었다: 무인 요청이거나 `conn`이 그 요청을 받은 원 연결일 때만 보인다. 핸들러는 `conn`을
   넘기지 않으므로(기본 `None`) 어떤 클라이언트에게도 대화형 요청이 노출되지 않는다. 대화형
   요청은 원래 s2c `approval.request`로 직접 전달되므로 TUI가 목록에서 다시 볼 필요가 없다.
   나중에 "내 것은 목록에도 보이게" 하고 싶으면 핸들러에서 `conn`만 넘기면 된다.
4. **인증된 연결 전체 브로드캐스트를 위해 `EventHub`에 `register_client`가 생겼다.** 기존
   `EventHub.notify`는 세션을 구독한 연결에만 나갔고, 세션을 하나도 만들지 않은 TUI는 공유 큐
   알림을 못 받는다. `system.hello` 성공 시 연결을 `hub.register_client(conn)`로 등록하고
   `notify()`가 구독자 ∪ 클라이언트로 팬아웃한다. `session.event` 팬아웃(`emit`)은 그대로
   세션 구독자에게만 간다 — 다른 세션의 이벤트가 새어나가지 않는다. 연결이 닫히면 기존
   `hub.unsubscribe(conn)` 경로가 클라이언트 목록에서도 지운다.
5. **어댑터는 콜백을 별도 콜백 함수가 아니라 `InboundMessage`로 전달한다.** `PlatformAdapter`
   프로토콜을 `start/send/stop` 셋으로 유지하려고, 버튼 눌림은 `callback_data`(그리고 플랫폼이
   응답에 쓰는 `callback_id`)가 채워진 `InboundMessage`로 온다. 라우터가 `apr:<requestId>:allow|deny`를
   먼저 보고 승인으로 처리하고, 아니면 프롬프트로 넘긴다.
6. **바인딩 저장소는 `session/store.py`가 아니라 `gateway/router.py` 안의 `BindingStore`다.**
   같은 `state.db` 파일의 `gateway_bindings` 테이블을 쓰지만 연결을 따로 연다. 데몬 기동 시
   세션 스토어 배선 전에 복원할 수 있고, 다른 스토리가 편집 중인 파일에 메서드를 더하지 않기
   위해서다. `Daemon.start`가 소켓을 연 뒤 `GatewayRouter.restore()`를 부르고, 복원에 실패한
   바인딩(자격증명 사라짐 등)은 지우지 않고 `state="inactive"`로 남겨 `gateway.list`에 보인다.
7. **Slack은 Socket Mode만 구현했다.** 계약이 "Socket Mode 또는 폴링"을 허용하는데, 폴링은
   어댑터가 채널 목록을 알아야 해서 바인딩 모델과 맞지 않는다. app-level 토큰(`xapp-`)이 없으면
   어댑터는 **송신 전용**으로 뜨고 경고 한 줄을 남긴다 — 스케줄러 배달에는 그대로 쓸 수 있다.
   자격증명이 두 개라서 `credentials.json` 값은 문자열 또는
   `{"token": "xoxb-…", "app_token": "xapp-…"}` 객체를 모두 허용한다.
8. **Hermes 게이트웨이 코드는 벤더링하지 않았다.** `/tmp/hermes-ref/plugins/platforms/telegram/adapter.py`는
   6.5k 줄이고 Hermes의 룸/그랜트/미디어 캐시 모델에 엮여 있다. 우리가 쓰는 표면은 Bot API 세 개
   (`getUpdates`·`sendMessage`·`answerCallbackQuery`)뿐이라 httpx로 직접 썼다. `docs/vendoring-map.json`은
   건드리지 않았다.
9. **테스트용 가짜 플랫폼은 `SNOWPEA_GATEWAY_FAKE=1`로 켠다.** `SNOWPEA_PROVIDER=fake:`가 모델을
   바꾸는 것과 같은 방식으로, 이 환경변수가 켜지면 모든 플랫폼이 `FakeAdapter`로 만들어진다.
   재시작 복원 테스트가 자격증명·소켓 없이 데몬 기동 경로를 그대로 지나가게 하려면 팩토리 주입
   만으로는 부족했다(복원은 `Daemon.start` 안에서 일어난다).
10. **`respx`를 도입하지 않았다.** 텔레그램/디스코드/슬랙 어댑터 테스트는 `httpx.MockTransport`
    (httpx 내장)로 실제 요청 빌드와 응답 파싱을 검증한다. 새 개발 의존성이 없다.
11. **CLI `snowpea gateway bind`의 target 축약형.** RPC는 객체를 받지만 셸에서 JSON을 치는 건
    불편해서 `agent:<name>` / `session:<id>` / `new:<workdir>` 축약형을 받고, `{`로 시작하면 JSON
    그대로 파싱한다(`cli/commands.parse_target`).
12. **`approvals.jsonl`에 `unattended` 플래그가 붙었다.** 계약 §4의 레코드 스펙대로 추가했고,
    기존 필드(`args`·`risk`·`code`)는 그대로 둬서 이전 줄과 섞여도 읽힌다.
