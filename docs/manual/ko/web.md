# snowpea web

`snowpea web`은 에이전트를 브라우저에서 엽니다. snowpea IDE와 같은 화면 — 같은 사이드바, 대화, 궤적(Trajectory), 독 — 을 로컬 데몬이 서비스하므로 따로 설치할 것이 없고 어떤 데이터도 내 컴퓨터 밖으로 나가지 않습니다.

```bash
snowpea web            # start the daemon if needed, print the address, open it
snowpea web --no-open  # print the address only
```

주소는 `http://127.0.0.1:<port>/web/?token=…` 형태입니다. 토큰은 데몬의 것(`$SNOWPEA_HOME/daemon.json`에 있는 그 토큰)이며, 페이지는 이를 해당 브라우저 탭에 보관하고 주소창에서는 지웁니다. 토큰을 가진 사람은 누구나 에이전트를 조종할 수 있으므로 주소를 채팅이나 티켓에 붙여 넣지 마세요. 이 주소는 데몬이 도는 컴퓨터에서만 열립니다.

## 다른 컴퓨터에서

> **링크(또는 사용자 이름과 비밀번호)를 가진 사람은 누구나 사용자 본인으로 snowpea를 쓸 수 있고, 이 컴퓨터에서 명령을 실행할 수 있습니다. 링크는 SSH 키처럼 다루세요. 아무에게도 공유하지 말고, 비밀번호 방식을 쓰고, 앞에 HTTPS(터널이나 리버스 프록시)를 두세요.**

원격 로그인은 제한된 계정이 아닙니다. 어느 폴더에서든 세션을 열고, `auto`로 바꾸고, 프롬프트를 보내고, 자기 세션의 승인에 스스로 답할 수 있습니다. 이 컴퓨터에서 사용자 본인의 셸을 쓰는 것과 같습니다. snowpea의 화면으로는 할 수 없는 일은 [이 컴퓨터에 남겨 두는 것](#이-컴퓨터에-남겨-두는-것)에 정리했습니다. 그 목록은 실수나 잠깐 빌려 쓴 세션이 클릭 한 번으로 그런 것을 바꾸지 못하게 하려는 것이지, 링크를 가진 사람을 막는 보안 경계가 아닙니다.

가장 간단한 방법은 여전히 ssh 터널입니다. 따로 열리는 포트가 없고 연결도 암호화됩니다.

```bash
ssh -L <port>:127.0.0.1:<port> host
```

같은 네트워크의 노트북이나 휴대폰에서 바로 열려면 `snowpea web`에 주소와 포트를 주면 됩니다. 데몬이 재시작 없이 바로 두 번째 listener를 열고, 루프백 listener는 지금처럼 그대로 동작합니다.

```bash
snowpea web --host 0.0.0.0 --port 8787           # 비밀번호 없이 접속 링크로
snowpea web --host 0.0.0.0 --port 8787 --save    # 데몬을 다시 시작해도 같은 설정으로
```

비밀번호가 없으면 다른 컴퓨터는 출력된 **접속 링크** `http://<이 컴퓨터의 LAN 주소>:8787/web/?t=<토큰>`으로 엽니다. 토큰은 데몬 토큰과 다른, 이 용도만의 256비트 무작위 키이며 `credentials.json`(권한 0600)에 보관됩니다. 첫 방문에서 로그인 쿠키로 바뀌고, 페이지는 토큰이 빠진 같은 주소로 이동하므로 주소 표시줄에 더는 보이지 않고 이후 요청에도 실리지 않습니다. 다만 어떤 브라우저는 토큰이 들어 있는 첫 주소를 방문 기록에 남기고, 링크를 복사해 붙인 채팅이나 메일에도 남아 있을 수 있습니다. 여러 사람이 쓰는 기기라면 사용한 뒤 링크를 바꾸세요(`snowpea web token --rotate`). 링크를 가진 사람은 이 컴퓨터를 다룰 수 있으니 비밀번호처럼 다루세요.

```bash
snowpea web token              # 링크를 다시 출력
snowpea web token --rotate     # 새 토큰: 이전 링크는 더 이상 열리지 않고 모두 로그아웃
```

로그인 화면을 쓰려면 사용자 이름과 비밀번호를 정합니다. 그러면 링크만으로는 열리지 않고 둘 다 묻습니다.

```bash
snowpea web --host 0.0.0.0 --port 8787 --user me --password-stdin   # stdin에서 한 줄
SNOWPEA_WEB_PASSWORD=… snowpea web --host 0.0.0.0 --port 8787 --user me
snowpea web --host 0.0.0.0 --port 8787 --user me --password '…'      # 동작하지만 아래 참고
snowpea web password             # 나중에 설정하거나 변경(두 번 묻습니다)
snowpea web password --clear     # 접속 링크 방식으로 돌아가기
```

명령줄의 `--password`도 동작하지만, 셸 기록과 프로세스 목록에 보인다는 경고를 출력합니다. `--password-stdin`이나 `SNOWPEA_WEB_PASSWORD`를 권장합니다. 비밀번호는 `settings.json`이 아니라 `credentials.json`에 salt를 넣은 scrypt 해시로만 저장합니다.

`snowpea web status`는 원격 접속이 켜졌는지, 방식(접속 링크 또는 비밀번호), 주소와 링크, 사용자 이름, 비밀번호 설정 여부, 로그인한 세션 수, 그리고 `settings.json`이 지금 실행 중인 것과 다른지(다음 데몬 시작 때 달라짐, `--save`로 현재 설정을 저장)를 보여 줍니다. 원격 접속 설정 화면이 있는 클라이언트도 같은 내용을 보여 줍니다(원격 로그인으로 연 페이지에서는 읽기 전용).

`settings.json`에 설정하고 데몬을 다시 시작하는 방법도 그대로 쓸 수 있습니다.

| 설정 (`web.remote.…`) | 기본값 | 의미 |
|---|---|---|
| `enabled` | `false` | 두 번째 listener를 시작합니다. |
| `host` | `0.0.0.0` | listen할 주소(`0.0.0.0`은 모든 인터페이스). |
| `port` | `8787` | listen할 포트. |
| `username` | `""` | 로그인할 수 있는 단 하나의 계정. |
| `sessionHours` | `12` | 로그인이 유지되는 시간. |
| `allowedOrigins` | `[]` | WebSocket이 추가로 받아 줄 페이지 origin(예: 프록시 뒤의 `https://snowpea.example.com`). |
| `trustProxy` | `false` | 직접 운영하는 리버스 프록시의 `X-Forwarded-Proto` / `X-Forwarded-For`를 믿습니다. 켜기 전에 [리버스 프록시 뒤에서](#리버스-프록시-뒤에서)를 읽으세요. |
| `maxMode` | `auto` | 원격 로그인이 쓸 수 있는 가장 넓은 모드: `plan`, `accept`, `auto`. [모드 제한](#모드-제한-maxmode) 참고. 재시작 없이 바로 적용됩니다. |

비밀번호는 있는데 사용자 이름이 없으면 데몬은 루프백으로만 시작하고, 이유를 로그에 남기며, `snowpea web`도 그 이유를 알려 줍니다.

### 원격 로그인이란

두 번째 listener로 들어온 연결은 링크든 비밀번호든 모두 **원격 로그인**입니다. 원격 로그인은 사용자 본인입니다. 어느 폴더에서든 세션을 열고, 모드를 정하고, 프롬프트를 보내고, 그 세션의 승인에 답하고, 세션 폴더의 파일을 읽고 씁니다. 따라서 링크나 비밀번호를 가진 사람은 이 컴퓨터에서 사용자 본인으로 프로그램을 실행할 수 있습니다. 긴 비밀번호를 쓰고, 링크는 남에게 보이지 말고, 쓰지 않을 때는 원격 접속을 끄세요(클라이언트의 원격 접속 설정 화면, 또는 `web.remote.enabled: false`로 두고 데몬 재시작).

**평문 HTTP입니다.** 접속 링크, 비밀번호, 모든 작업이 암호화되지 않은 채 오갑니다. 믿을 수 있는 네트워크 밖이라면 TLS(Caddy, nginx 같은 리버스 프록시) 뒤에 두거나 VPN 또는 위의 ssh 터널로 접속하세요.

### 이 컴퓨터에 남겨 두는 것

원격 로그인이 snowpea의 화면으로는 할 수 없는 일이 있습니다. 페이지는 로컬 연결이 필요하다고 알려 줍니다. 실수로, 또는 잠깐 빌려 쓴 세션에서 클릭 한 번으로 바뀌지 않도록 이 컴퓨터에 남겨 두는 것입니다. 링크를 가진 사람을 막는 벽이 아닙니다. 그 사람은 명령을 실행할 수 있으므로, 이것을 보안 경계로 믿으면 안 됩니다.

- **원격 접속 자체**: listener, 주소, 비밀번호, 링크, `maxMode`. 데몬 설정, 업데이트, 재시작, 확장도 같습니다.
- **자비스**: 자비스 모드를 켜는 것, 자비스에게 권한을 주는 것(위임 grant — 원격 로그인도 grant를 거두고, 세션을 넘겨받고 되돌려 주는 것은 할 수 있습니다), 외부 CLI의 경로, 외부 세션을 unrestricted로 여는 것. **브리핑**(사용자의 말을 담아 반복 실행되는 자비스 작업)은 원격 로그인이 끄는 것만 할 수 있고, 자비스에게 바꾸라고 시켜도 마찬가지입니다.
- **보안 목록**(차단 명령, 보호 경로)과 **프로젝트 신뢰**.
- **허용 규칙(allowlist).** 원격 로그인은 규칙을 추가할 수 없습니다. 승인에 "항상" 또는 "이 프로젝트에서"로 답해도 그 답은 세션이 끝날 때까지만 적용되고 규칙은 저장되지 않습니다.
- **메신저**: 토큰, 사용자·채널 id, 켜고 끄는 스위치, 채팅을 세션이나 이름 있는 에이전트에 연결(bind)하는 것.
- **이 컴퓨터가 실행하는 프로그램**: 명령을 실행하는 MCP 서버(`command`, `args`, `env`, `cwd`)와 서버에 대한 보안 경고를 무시하고 진행하는 것, 언어 서버의 명령, 오디오 명령 엔진·재생기·녹음기, 미디어 스튜디오 서버(`media.*`). 로컬에서 저장해 둔 명령 서버는 계속 테스트하거나 켜고 끌 수 있습니다.
- **저장된 비밀 값이 전송되는 곳.** 원격 로그인은 URL만 있는 MCP 서버를 추가할 수 있지만 `${변수}`를 쓰는 서버는 추가할 수 없고, 이미 저장된 서버의 URL, 헤더, OAuth 설정은 바꿀 수 없습니다. snowpea는 그런 변수를 `credentials.json`에서 채워 그 항목이 가리키는 곳으로 보내기 때문입니다. 원격 로그인이 추가한 서버에는 저장된 자격 증명이 전달되지 않습니다. 제공자의 base URL(모든 프롬프트와 키가 어디로 가는지 정합니다), 스킬 레지스트리 주소, 검색·브라우저 제공자의 주소(`search.credentials`나 `browser.credentials` 아래의 `url`, `base_url`, `endpoint`, `host`, `proxy` 필드나 `_URL`로 끝나는 필드)도 같습니다. 검색 제공자는 설정이나 데몬 환경 변수의 키를 그 주소로 보내기 때문입니다. 제공자의 **계정**도 이 컴퓨터에 남겨 둡니다. 키, 로그인(`provider.loginWeb`, `/login`)과 로그인이 남기는 OAuth 기록, MCP 서버 로그인 마무리가 그렇습니다. 그렇지 않으면 트래픽, 요금, 로그가 다른 사람의 계정으로 옮겨 가고 링크를 바꾼 뒤에도 그대로 남을 수 있습니다. 원격 로그인은 제공자의 모델을 고르고 키를 지우는 것은 계속 할 수 있습니다.
- **스킬, 에이전트, 명령.** 원격 로그인은 방법을 설명하기만 하는 전역 스킬을 쓸 수 있습니다. 프로젝트의 스킬·에이전트·명령, 전역 에이전트나 명령, 내장된 것과 같은 이름을 쓰는 것, 머리말에 `allowed-tools`, `autoInject`, `permission`, `hooks`, `model`, `tools`를 정한 스킬은 쓸 수 없습니다. 에이전트를 만들거나 팀 가이드를 바꿀 수 없고, 스킬과 플러그인은 레지스트리(`registry:<이름>`)나 마켓플레이스(`<마켓플레이스>/<플러그인>`)에서만 설치하며 폴더, 링크, git URL에서는 설치할 수 없습니다.
- **무엇이 실행될지 정하는 프로젝트 파일**(파일 패널로): `.snowpea`와 `.claude`의 hooks, commands, skills, agents, `.mcp.json`(MCP 화면으로도: 원격 로그인은 전역 범위에서만 서버를 추가·변경·삭제합니다), `.git/hooks`, `.git/config`. 프로젝트 설정에서는 기본 모드, 팀, 모델 배정만 바꿀 수 있습니다.
- **보안 목록이 보호하는 것.** 보안 목록이 막는 파일은 파일 패널로도 아무도 쓸 수 없고, 에이전트라면 사용자에게 물어봐야 하는 파일은 이 컴퓨터에서만 쓸 수 있습니다. 기본 `essential` 프리셋에는 로그인하거나 셸을 열 때 실행되는 것이 들어 있습니다: `~/.ssh`, `~/.bashrc`, `~/.zshrc`, `~/.profile` 등 셸 시작 파일, `~/.config/autostart`, `~/.config/systemd/user`, `LaunchAgents`/`LaunchDaemons` 폴더. 에이전트에게도 똑같이 적용됩니다.
- 명령 `/update`, `/desktop`, `/allow`, `/setup`, `/allowlist remove`, `/agent create`.

원격 로그인이 에이전트나 파일 패널로 프로젝트 폴더에 쓴 내용 때문에, 그 프로젝트에서 신뢰해 둔 파일이 바뀔 수 있습니다. 그러면 snowpea는 이 컴퓨터에서 다시 확인하고 신뢰할 때까지 그 신뢰된 내용(hooks, MCP 서버, 프로젝트 기본 모드)을 적용하지 않습니다.

이 규칙들의 한계를 분명히 적어 둡니다.

- "원격 로그인이 저장한 것"이라는 표시(MCP 항목의 `savedBy`, 스킬 폴더의 `.saved-by` 파일, 작업의 `createdBy`)는 에이전트의 셸이 다시 쓸 수 있는 파일 안에 있습니다. 남겨진 것을 보이게 하고 좁혀 줄 뿐, 증명은 아닙니다.
- 이 컴퓨터에서 추가한 MCP 서버는 데몬 환경의 어떤 `${변수}`든(`SNOWPEA_*` 제외) 그리고 `credentials.json`의 어떤 자격 증명 이름이든 채워 넣습니다. 믿는 서버만 추가하세요.
- 원격 로그인이 쓴 메모리 항목에는 그런 표시가 없습니다.
- 사용자에게 연결된 메신저 채팅은 다른 기기에서의 사용자 본인입니다. `maxMode`와 위 규칙은 이를 좁히지 않습니다.

### 모드 제한 (`maxMode`)

`web.remote.maxMode`는 원격 로그인이 쓸 수 있는 가장 넓은 모드입니다. `accept`로 두면 원격 로그인은 세션을 `auto`(또는 "plan 후 auto")로 바꿀 수 없고, `auto` 세션이나 예약 작업을 만들 수 없으며, 이미 `auto`인 세션이나 작업에 프롬프트를 보내거나 끼어들거나 실행할 수 없습니다. 읽기, 모드 낮추기, 승인에 답하기는 가능합니다. `plan`으로 두면 `accept`도 같은 취급입니다. 원격 로그인이 예약한 작업도 이 한도를 넘는 모드로는 실행되지 않으며, 나중에 한도를 낮춘 경우에도 마찬가지입니다. **자비스**에게 시킨 경우도 같습니다. 원격 로그인이 시작한 자비스 턴에서 자비스가 시작하거나 프롬프트를 보내거나 예약하는 일은 원격 로그인의 것으로 판단합니다. 사용자에게 연결된 메신저 채팅은 `maxMode`로 제한되지 않습니다.

```bash
snowpea web max-mode accept   # 이 컴퓨터에서 설정, 바로 적용
snowpea web max-mode          # 현재 값 보기(`snowpea web status`에도 나옵니다)
snowpea web max-mode auto     # 다시 제한 없음(기본값)
```

이 설정으로 얻는 것을 분명히 알아 두세요. 원격 로그인이 **사람 없이** 돌리는 작업을 막습니다. 원격 로그인이 시작한 일은 누군가 명령마다 승인해야 실행됩니다. 하지만 링크를 가진 사람 자체는 막지 못합니다. 그 승인에 답하는 사람이 바로 그 사람이기 때문입니다. 이 값은 이 컴퓨터에서만 설정할 수 있고 원격 로그인은 바꿀 수 없습니다.

### 예약 작업

원격 로그인이 만든 예약 작업은 — 예약 화면으로 만들든, `/schedule`로 만들든, 에이전트나 자비스에게 예약을 시켜서 만들든 — 작업 목록에 그렇게 표시되고, `snowpea web status`가 그 수를 보여 줍니다. 그런 작업은 그 로그인이 끝난 뒤에도 계속 실행되므로, 다른 사람이 페이지를 쓴 뒤에는 목록을 확인하세요. 이 수(클라이언트 원격 접속 화면의 `remoteLeft`)에는 원격 로그인이 저장한 MCP 서버와 전역 스킬도 들어가며, 메모리 항목은 들어가지 않습니다. 원격 로그인은 자비스 브리핑을 켜거나 바꿀 수 없습니다(위 참고). 원격 로그인이 만든 작업은 결과를 앱 안에서만 알리며(메신저 채팅으로 보낼 수 없습니다), 원격 로그인은 자신이 만든 작업만 바꾸거나 끄거나 취소하거나 삭제할 수 있습니다. 로컬에서 만든 작업은 보고, 저장된 그대로 실행하는 것만 가능합니다.

### 로그인 제한

- 한 주소에서 5분 안에 5번, 또는 전체에서 20번 로그인에 실패하면(틀린 비밀번호와 틀린 링크를 함께 셉니다) 그 5분이 끝날 때까지 로그인이 느려집니다. 이후의 비밀번호 시도는 먼저 기다립니다(1초에서 시작해 최대 30초까지 두 배씩). 다른 곳의 실패가 맞는 비밀번호를 거절하게 만들지는 않고, 기다리게 할 뿐입니다. 틀린 시도에는 "시도가 너무 많습니다"라고 답합니다. IPv6 네트워크(/64)는 주소 하나로 셉니다.
- 한 주소의 비밀번호 확인은 한 번에 하나씩이고, 그 뒤에 최대 4개까지 기다릴 수 있습니다. 그보다 많거나 — 전체에서 64개가 넘게 기다리고 있으면 — 시도는 확인하지 않고 바로 "시도가 너무 많습니다"라고 답합니다. 그래서 같은 주소를 쓰는 사람(사무실이나 모바일 네트워크)이나 아주 많은 주소에서 몰아치는 사람이 그러는 동안에는 로그인이 **늦어질** 수 있습니다. 하지만 그것으로 링크나 비밀번호를 더 빨리 알아낼 수는 없습니다. 접속 링크는 바로 확인되며 비밀번호 확인 뒤에서 기다리지 않습니다.
- 이 제한은 주소 하나를 느리게 할 뿐입니다. 아주 많은 주소에서 동시에 시도하는 사람까지 막지는 못합니다. 데몬은 비밀번호를 한 번에 두 개씩 확인하므로 전체로는 초당 20번쯤 추측할 수 있습니다. 짧은 비밀번호는 이를 견디지 못하고, 긴 비밀번호와 접속 링크(256비트 키)는 견딥니다. 로그인 성공과 실패는 클라이언트 주소와 함께 로그에 남고, 비밀번호와 토큰은 남지 않습니다.
- 로그인은 쿠키(`HttpOnly`, `SameSite=Strict`, HTTPS에서는 `Secure`)입니다. 세션은 데몬 메모리에만 있어서 데몬을 다시 시작하면 모두 로그아웃됩니다. 비밀번호를 바꾸거나 지우거나 토큰을 바꾸면 모든 사람이 즉시 로그아웃되고 열려 있던 페이지의 연결도 모두 닫힙니다. 만료된 로그인은 그다음 요청부터 동작하지 않고, 열려 있던 페이지는 로그인 화면으로 돌아갑니다.
- 원격 listener는 페이지, 로그인, WebSocket만 제공합니다(`/health`, `/version`, 스키마 없음). WebSocket은 다른 origin의 페이지를 거부합니다.

### 리버스 프록시 뒤에서

직접 운영하는 리버스 프록시(Caddy, nginx)로 TLS를 앞에 두고, 페이지 주소를 `allowedOrigins`에 넣고, `trustProxy: true`로 설정하면 데몬이 방문자의 주소와 `https` 여부를 프록시의 헤더에서 읽습니다. `trustProxy`는 그 프록시 말고는 아무도 이 포트에 닿지 못할 때**만** 켜세요. listener를 루프백(`--host 127.0.0.1`)이나 프록시 전용 네트워크에 bind하거나 방화벽으로 막으면 됩니다. 그렇지 않으면 포트에 직접 닿는 사람이 클라이언트 주소를 마음대로 꾸며 보내 주소별 로그인 제한을 피할 수 있습니다.

## 화면 구성

레이아웃은 DeepSeek Harness 웹 클라이언트를 따릅니다. 세 개의 열이고 가운데가 대화입니다.

| 열 | 들어 있는 것 |
|---|---|
| 왼쪽 — 사이드바 | **새 세션**, 플러그인, 자동화 작업, 더보기(그 밖의 화면: 스킬, 스케줄, 설정…), 그리고 **작업 공간**: 프로젝트 폴더마다 하나의 그룹이 있고 그 안에 대화가 들어 있으며, 고정한 대화가 먼저 나옵니다. 행의 점은 턴이 실행 중이거나, 승인을 기다리거나, 읽지 않은 내용이 있다는 뜻입니다. 행 메뉴에서 고정, 이름 변경, 포크, ID 복사, 보관을 할 수 있습니다. |
| 가운데 — 대화 | 대화 제목, 이 대화가 위임되었거나 포크되어 나온 부모 대화들, 그리고 두 개의 탭이 있는 헤더: **대화**(메시지, 툴 카드, 입력창)와 **궤적(Trajectory)**(아래 참고). |
| 오른쪽 — 독 | 대화 옆에 열리는 탭들: 파일, 작업 공간 파일 트리, 계획, 위임된 작업, 변경 사항, 그리고 IDE에서는 터미널. 창을 나눌 수 있고 탭은 창 사이를 옮길 수 있습니다. 레이아웃은 이 브라우저에서 대화별로 저장됩니다. |

사이드바 너비는 280 px(가장자리를 끌어 264~420 사이로 조절)이고, 1024 px 미만에서는 레일로 접히며, 768 px 미만에서는 서랍이 됩니다. `Ctrl/⌘ B`로 토글합니다. 독은 창의 45 %로 열리고, 지정한 너비를 기억하며, 70 %를 넘지 않고, 대화가 400 px보다 좁아지게 두느니 닫힙니다. `Ctrl/⌘ J`로 토글합니다.

독의 빈 패널에는 **시작** 탭이 나오며, 워크스페이스 파일, 변경 사항, 계획 카드가 있습니다(터미널 카드는 IDE 전용). 상태 표시줄은 연결 여부를 보여 주며, 열린 탭이 있으면 데몬이 유휴 상태라는 이유로 종료되지 않습니다.

## 독에서 열리는 파일

대화가 언급한 파일은 새 창이 아니라 독의 탭으로 열립니다.

- 파일로 가는 마크다운 링크(`[math.ts]` + `(math.ts)`), 상대 또는 절대 경로, Windows 경로
- 줄 또는 범위: `#L24`, `#L24-L30`, `:24`, `:24-30`
- `` `src/app.ts` ``와 같은 인라인 코드 — 단, 그 턴이 읽거나 쓴 파일을 가리킬 때만
- 그 턴이 읽거나 쓴 파일을 가리키는 답변 속 파일명(예: `notes.md`). 그 밖의 파일명은 일반 텍스트로 남고, 일반 텍스트는 명시적인 http(s), mailto: 또는 www. 주소일 때만 링크가 됩니다.
- 답변 아래의 파일 칩과 아티팩트 카드

같은 파일을 다시 열면 그 탭으로 이동합니다. 미리보기는 IDE의 것입니다: 구문 강조된 코드, 마크다운, 이미지, PDF, 스프레드시트, 오피스 문서, 노트북. HTML 파일은 기본적으로 **정적**으로 표시됩니다(정제됨, 스크립트 없음, 엄격한 콘텐츠 보안 정책). **스크립트 실행**으로 바꾸면 격리된 프레임에서 불러오며, 그 프레임은 자체 스크립트를 실행할 수 있지만 페이지, 쿠키, 데몬에는 접근할 수 없습니다.

브라우저에서 파일은 데몬(`fs.*`)을 통해 읽으며, 대화의 폴더 안에서만 읽습니다: 작업 디렉터리, 작업 공간, 첨부 파일. 그 밖의 경로는 에이전트의 도구가 거부하는 것과 똑같이 거부됩니다.

## 궤적(Trajectory)

**궤적(Trajectory)** 탭은 에이전트가 한 일을 채팅이 아니라 단계별로 보여 줍니다. 턴마다 하나의 밴드가 있고, 그 안의 모델 호출마다 텍스트, 추론, 툴 호출을 담은 단계가 있으며, 각 툴 호출에는 인자, 결과, 걸린 시간이 표시됩니다. 위임된 작업은 시작된 자리에 나타나고, 클릭하면 자식 대화가 독에서 열립니다. 툴 호출 안의 파일도 위와 같이 독에서 열립니다. 세션의 이벤트 로그(`session.trajectory`)로 만들어지므로 실행 중인 턴이든, 끝난 턴이든, 내일 다시 이어가는 대화든 똑같이 보입니다.

## 포크, 고정, 보관

끝난 턴에서 대화를 **포크**할 수 있습니다. 그 턴까지의 기록을 가진 새 대화가 시작되고 원래 대화는 그대로 남습니다. 새 대화의 헤더에 어디서 왔는지 표시됩니다. 턴 이전으로 파일을 되돌리는 것(체크포인트)은 전과 같이 동작합니다. 포크는 지금 것을 잃지 않고 다른 방향을 시도하기 위한 기능입니다.

**고정**은 대화를 작업 공간의 맨 위에 둡니다. **보관**은 삭제하지 않고 사이드바에서 숨깁니다(사이드바의 보기 옵션에서 보관된 대화를 다시 볼 수 있습니다).

## 브라우저가 할 수 없는 것

페이지는 운영 체제에 접근할 수 없으므로 다음은 IDE와 터미널 UI에서만 할 수 있습니다.

- 터미널(터미널에서 열기, 새 터미널)
- 로컬에서 실행되는 git 동작, 그리고 폴더에서 보기 / 시스템 앱으로 열기
- 터미널, 파일, 워크트리 화면, 연결 관리자와 앱 자동 업데이트(이 주소들은 대화로 돌아갑니다)
- 기본 폴더 선택기 — 작업 공간은 경로를 입력해 추가하세요

이 기능의 버튼은 실패하는 대신 브라우저에서 숨겨집니다.

## 페이지는 어디서 오는가

웹 빌드는 snowpea 패키지에 들어 있고 데몬이 `/web/` 아래에서 서비스합니다. `index.html`은 캐시되지 않고 다른 모든 파일은 이름에 콘텐츠 해시가 있으므로, 업그레이드 후 새로고침하면 항상 새 버전을 받습니다. 개발할 때는 `SNOWPEA_WEB_DIST`로 데몬이 다른 빌드를 가리키게 할 수 있습니다.

```bash
# in snowpea-ide
npm run build:web
# then, with a separate home so your own daemon is not touched
SNOWPEA_WEB_DIST=$PWD/out/web snowpea --home /tmp/snowpea-dev web
```

빌드가 없으면 `snowpea web`이 그렇게 알려 주고 주소는 `404`로 응답합니다.
