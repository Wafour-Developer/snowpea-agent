# 메신저 게이트웨이

게이트웨이는 채팅 플랫폼을 세션 또는 이름 있는 에이전트에 연결합니다. 그 대화방의 메시지는 프롬프트가 되고, 에이전트의 답은 다시 메시지로 돌아오며, 승인 요청은 버튼으로 도착합니다. v0.1에서 완전히 지원되는 플랫폼은 Telegram입니다. Discord와 Slack은 같은 인터페이스를 구현하고 있고 전달은 되지만, 실전 검증은 상대적으로 덜 쌓여 있습니다.

## 먼저 자격 증명부터

```bash
snowpea setup --gateway telegram --token 123456:ABC-your-bot-token
```

토큰은 `$SNOWPEA_HOME/credentials.json`에 `0600` 권한으로 들어갑니다. 대신 환경 변수로 export한 뒤 바인딩할 때 그 이름을 참조해도 됩니다. 어느 쪽이든 토큰이 `settings.json`에 쓰이는 일은 없고, 로그 한 줄에도 나타나지 않습니다.

## 바인딩

```bash
snowpea gateway bind telegram TELEGRAM_BOT_TOKEN agent:scribe --user 987654
snowpea gateway bind telegram TELEGRAM_BOT_TOKEN new:~/src/api --channel 123456 --user 987654
snowpea gateway list --json
snowpea gateway unbind <binding-id>
```

세 위치 인자는 순서대로 플랫폼, 자격 증명 참조(`credentials.json`의 키 또는 환경 변수 이름), 대상입니다:

| 대상 | 의미 |
|---|---|
| `agent:<name>` | 자기 메모리 네임스페이스를 가진 이름 있는 상시 에이전트 |
| `session:<id>` | 기존 세션 |
| `new:<workdir>` | 첫 메시지가 오면 그 디렉터리에 세션을 새로 만듦 |

`--channel`은 바인딩을 특정 채팅 id 하나로 제한합니다. `--user`는 승인을 결정할 수 있는 플랫폼 사용자를 지정합니다. 둘 다 설정하세요. `--user`가 없으면 승인에 답할 권한을 가진 사람이 아무도 없는 상태가 되고, 게이트웨이는 누가 버튼을 눌러도 무시합니다.

## 봇 만들기

**Telegram.** [@BotFather](https://t.me/BotFather)에게 `/newbot`을 보내고 토큰을 받아 둡니다. 채팅 id는 봇에게 처음 메시지를 보냈을 때 데몬 로그에 찍히는 숫자입니다. long polling 방식이라 공개 URL도 webhook도 필요 없습니다.

**Discord.** 애플리케이션을 만들고 봇 유저를 추가한 뒤 message content intent를 켜고, 서버에 초대하고, 봇 토큰을 받아 둡니다. 채널 id는 채널 URL의 마지막 경로 조각입니다.

**Slack.** 앱을 만들고 `chat:write`와 워크스페이스에 필요한 이벤트를 추가한 뒤 설치하고, 봇 토큰을 받아 둡니다. 대상으로는 채널 이름이나 id를 씁니다.

## 대화하기

봇에게 메시지를 보내면 바로 세션이 시작됩니다. 슬래시 명령은 터미널에서와 완전히 똑같이 동작하는데, 명령 레지스트리가 UI가 아니라 코어에 있기 때문입니다:

```
/mode
/ralph fix the failing integration test
/schedule "매일 09:00" "어제 커밋 요약" --channel telegram:123456
```

게이트웨이가 만든 세션은 `session.list`에 출처와 함께 뜨므로, 같은 데몬에 붙은 TUI에서도 그 대화방이 지금 뭘 하고 있는지 볼 수 있습니다.

## 무인 승인

게이트웨이나 스케줄러 세션에서 올라온 승인 요청은 무인 상태이고, 타이핑으로 직접 일으킨 승인과는 다르게 동작합니다:

- 붙어 있는 모든 클라이언트에 `approval.pending` 알림으로 방송되므로 TUI 승인 큐에도 뜹니다.
- 바인딩된 대화방에 허용·거부 버튼과 함께 전송됩니다.
- 어느 쪽이든 먼저 온 응답이 이깁니다. 나머지 모두는 결정 내용과 누가 결정했는지를 담은 `approval.resolved`를 받습니다.
- 바인딩된 `--user`만 대화방에서 답할 수 있습니다. 다른 사람의 버튼 클릭은 무시되고 로그로 남습니다.
- 아무 답이 없이 `approvals.timeoutSec`(기본 300초)이 지나면 거부됩니다.

TUI에서 타이핑으로 일으킨 승인은 그 화면에만 머물고 공유 큐에 절대 들어가지 않습니다. 이 경계가 핵심입니다 — 내 터미널의 프롬프트가 그룹 채팅으로 새어 나가지 않고, 채팅 승인을 낯선 사람이 대신 답할 수도 없습니다.

결정된 모든 건은 요청 id, 툴, 결정, 결정한 사람, 범위, 무인 여부와 함께 `$SNOWPEA_HOME/logs/approvals.jsonl`에 추가됩니다.

## 에이전트가 묻는 질문

`ask_user` 도구는 에이전트가 *당신에게* 묻는 것이고, 바인딩된 대화방에는 선택지마다 버튼이 달린 메시지로 도착합니다.

```text
❓ 렌더러
렌더링을 무엇으로 할까요? 여기서 고른 것이 엔진 통제력을 정합니다.
1. three.js (추천) — 빠른 시작, 엔진 통제력 낮음
2. Raw WebGL2 — 공수 큼, 완전한 통제
(번호로 답해 주세요 / reply with the number, or type your own answer)
[1. three.js (추천)] [2. Raw WebGL2] [✏️ 기타 / Other]
```

승인과 달리 대화방의 누구나 답할 수 있습니다. 질문은 아무 권한도 주지 않으므로 낯선 사람이 악용할 것이 없습니다. 버튼을 누르거나 번호를 그냥 적어도 됩니다 — `2`, 여러 개를 고르는 질문이면 `1,3`. 번호가 아닌 것은 자유 입력 답으로 받으며, "기타" 버튼이 요청하는 것도 그것입니다. 질문이 여러 개면 한 번에 하나씩 도착합니다. `questions.timeoutSec`(기본 600초)이 지나면 아무도 답하지 않았다고 에이전트에게 전달됩니다.

## 이름 있는 에이전트

이름 있는 에이전트는 자기 세션, 자기 메모리 네임스페이스, 자기 채널, 자기 잡을 가진 채 데몬 재시작을 넘겨 살아남습니다. 두 이름 있는 에이전트는 서로의 메모리를 읽을 수 없으므로, 하나에는 업무용 채널을, 다른 하나에는 개인용 채널을 맡겨도 안전합니다.

```bash
snowpea agents --json
```

`/agent create "<description>"`으로 하나 만들고 `gateway bind ... agent:<name>`으로 채널을 바인딩하면, 다음 데몬 기동 시 바인딩까지 함께 복원됩니다. 이름 있는 에이전트는 네 번째 keepalive 카운터라서, 하나라도 있는 데몬은 유휴 상태로 종료되지 않습니다.

## 보안

게이트웨이는 원격 실행 경로입니다. 그렇게 다루세요.

- `--user`를 바인딩하세요. 항상.
- 완전히 통제하지 못하는 대화방에서 닿는 작업에는 plan 모드를 우선하세요.
- 승인 요청은 일회용이고 요청 id 하나에 묶여 있어서, 버튼 클릭을 재전송해도 아무 일도 일어나지 않습니다.
- 자격 증명은 `0600` 파일에 있고, 가능하면 OS 키체인을 씁니다.
- `approvals.jsonl`을 가끔 들여다보세요. 내가 안 보는 사이에 무엇이 허용됐는지의 기록입니다.
