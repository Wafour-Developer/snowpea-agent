# 샌드박스 세션

`snowpea --docker`는 세션 전체를 일회용 Docker 컨테이너 안에서 실행합니다. 컨테이너가 snowpea 데몬을 돌리므로 에이전트, 툴, 셸, 설치, 메모리가 모두 그 안에 있고, 이 머신에는 터미널만 있습니다. 목적은 auto 모드입니다. 에이전트가 무엇을 설치하고 무엇을 망가뜨려도 되고, 떠나면 컨테이너는 버려집니다.

```
snowpea --docker
snowpea --docker --mode auto --cwd ~/src/app
snowpea --docker --docker-volume work
snowpea --docker my/snowpea-dev:1
```

`--cwd`(기본값은 현재 디렉터리), `--mode`, `--inline`은 평소처럼 동작합니다. 프로젝트 디렉터리는 컨테이너 안에 **같은 절대 경로로** 바인드 마운트되므로 프롬프트, 오류, diff의 경로가 양쪽에서 같은 뜻이고, 에이전트가 거기에 쓴 파일은 호스트에서 내 소유입니다.

| 플래그 | |
|---|---|
| `--docker [IMAGE]` | 세션을 컨테이너에서 실행합니다. `IMAGE`를 생략하면 snowpea가 빌드한 이미지를 씁니다 |
| `--docker-volume NAME` | 샌드박스의 `~/.snowpea`를 Docker 볼륨 `NAME`에 보관해 세션과 메모리가 컨테이너보다 오래 남게 합니다 |
| `--docker-keep` | 나갈 때 컨테이너를 멈추기만 하고 지우지 않습니다 |

## 동작 순서

1. Docker를 확인합니다. `docker`가 없거나, 데몬이 꺼져 있거나, 이 사용자가 쓸 수 없으면 할 일을 알려 주고 종료 코드 3으로 끝납니다. 로컬 세션으로 조용히 넘어가는 일은 없습니다.
2. 이미지를 처음 쓸 때 빌드하고 이후에는 재사용합니다(아래 참고).
3. 컨테이너는 내 사용자로, 새로 만든 무작위 토큰과 설정·자격 증명의 읽기 전용 사본을 갖고 시작합니다. 데몬이 듣는 포트는 Docker가 이 머신의 `127.0.0.1`에만 게시합니다.
4. 데몬이 `/health`에 응답할 때까지 기다린 뒤 그 포트에 터미널 UI를 붙입니다. UI는 이 데몬이 로컬이 아니라는 것을 알고 있어서 이 머신에서 데몬을 시작하거나 재시작하지 않습니다.
5. UI가 끝나거나 Ctrl+C를 누르면 컨테이너를 멈추고 지웁니다. snowpea 자체가 강제 종료되면 컨테이너가 입력이 닫힌 것을 알아채고 스스로 데몬을 멈춥니다.

UI가 제자리 업데이트로 종료(종료 코드 75)하면, 컨테이너가 아직 떠 있을 때는 같은 컨테이너에 다시 붙고 데몬이 사라졌다면 새 컨테이너를 시작합니다.

## 이미지

받아 올 이미지는 없습니다. snowpea가 패키지에 Dockerfile을 넣어 두고, 처음 요청할 때 `snowpea-sandbox:<버전>-<다이제스트>`를 빌드합니다. 베이스는 `python:3.12-slim`이고 git, ripgrep, ffmpeg, curl, npm이 포함된 Node.js, `ps`를 설치하며, **실행 중인 터미널과 같은 snowpea 버전**을 그 버전의 릴리스 태그에서 설치하므로 클라이언트와 데몬의 프로토콜이 늘 같습니다. 첫 빌드는 1GB쯤 내려받고 몇 분 걸립니다. 이후에는 `docker images snowpea-sandbox`에 보이며 매번 바로 시작합니다. snowpea 버전이 바뀌면 새 이미지를 빌드하므로 오래된 것은 `docker rmi`로 지우세요.

개발 체크아웃에는 설치할 릴리스 태그가 없습니다. 대신 `SNOWPEA_SANDBOX_SOURCE`에 wheel(`uv build --wheel`)이나 임의의 pip 요구 사항을 지정하세요.

```bash
SNOWPEA_SANDBOX_SOURCE=dist/snowpea_agent-0.2.80-py3-none-any.whl snowpea --docker
```

`IMAGE`를 주면 아무것도 빌드하지 않고 그 이미지를 실행합니다. 이미지에 이미 snowpea가 있어야 합니다. `PATH`의 `snowpea-core`, `sh`, 쓸 수 있는 `/home/snowpea/.snowpea`가 필요합니다. snowpea가 만든 이미지 위에 쌓는 것이 가장 쉽습니다.

```dockerfile
FROM snowpea-sandbox:0.2.80-ab12cd34
USER root
RUN apt-get update && apt-get install -y --no-install-recommends postgresql-client
USER snowpea
```

snowpea가 없거나 프로토콜 major가 다른 이미지는 컨테이너 자신의 오류와 함께 거부됩니다. minor만 다르면 경고입니다.

## 안에서 에이전트는 누구인가

컨테이너는 `--user <내 uid>:<내 gid>`로 실행되므로 에이전트가 프로젝트에 만든 파일은 root가 아니라 내 소유입니다. 안에 root는 없습니다. 에이전트는 자기 홈에 설치할 수 있지만(`pip install --user`, prefix를 준 `npm`, 내려받은 바이너리) `apt`는 쓸 수 없습니다. 시스템 패키지가 늘 필요하면 위처럼 직접 만든 이미지에 넣어 두세요. 컨테이너에는 특권 플래그가 없습니다. `--privileged`, 추가 capability, Docker 소켓, 호스트 네트워크가 없고 `no-new-privileges`가 켜져 있습니다.

snowpea는 `/`나 홈 디렉터리(또는 그 상위)를 마운트하지 않습니다. 샌드박스가 줄이려는 피해 범위 안에 내 모든 것이 들어가기 때문입니다. 프로젝트 디렉터리에서 실행하거나 `--cwd`를 지정하세요.

## 자격 증명과 설정

에이전트가 모델을 부르려면 제공자 키가 필요하므로, snowpea는 시작할 때 snowpea 홈(`~/.snowpea`, 또는 `--home`)의 다음 파일을 컨테이너의 `~/.snowpea`로 복사합니다.

- `settings.json` (제공자 선택과 각 `api_key`, 툴 설정),
- `credentials.json` (봇 토큰),
- `mcp-oauth.json` (MCP 서버 로그인, 있을 때만).

읽기 전용으로 마운트해 한 방향으로만 복사하므로 샌드박스에서 하는 어떤 일도 실제 파일에 닿지 않습니다. 세션, 메모리, 플러그인, 스킬은 복사되지 **않고** 환경 변수도 전달되지 않습니다.

> **에이전트는 이 비밀 값을 읽을 수 있습니다.** 샌드박스에서 실행되는 모든 것, 그리고 프롬프트 인젝션이 걸린 웹 페이지가 시키는 명령은 `~/.snowpea/settings.json`을 읽어 어딘가로 보낼 수 있습니다. 폐기할 수 있는 제공자 키, 가능하면 이 용도로 만든 키를 쓰고, 교체할 수 없는 키를 샌드박스용 설정에 넣지 마세요.

내 머신의 `localhost`를 가리키는 제공자는 컨테이너 안에서 동작하지 않습니다. 거기서 `localhost`는 컨테이너 자신이기 때문입니다. 대신 머신의 주소를 쓰세요.

터미널의 접근 토큰은 별개입니다. snowpea는 컨테이너마다 새 토큰을 만들어 컨테이너의 표준 입력으로 전달하므로, 어떤 명령줄(`ps`)에도, 환경 변수에도, `docker inspect`에도 나타나지 않습니다.

## 상태

기본적으로 컨테이너의 `~/.snowpea`는 임시입니다. 세션, 메모리, 에이전트가 준비한 모든 것이 컨테이너와 함께 사라집니다. `--docker-volume NAME`을 주면 이름 있는 Docker 볼륨에 보관하며, 다음에 `snowpea --docker --docker-volume NAME`으로 들어오면 이전 세션이 보입니다. 호스트의 설정은 시작할 때마다 볼륨의 사본 위에 다시 복사됩니다. 볼륨은 한 번에 컨테이너 하나만 쓸 수 있습니다. 지우려면 `docker volume rm NAME`.

`--docker-keep`은 멈춘 컨테이너를 파일시스템째 남겨서, 에이전트가 프로젝트 밖에서 한 일을 볼 수 있게 합니다. `docker cp <이름>:/경로 .` 다음 `docker rm <이름>`(snowpea가 두 명령을 출력합니다).

## 네트워크

컨테이너는 Docker 기본 브리지 네트워크를 씁니다. 인터넷과 로컬 네트워크에 닿을 수 있고, 호스트의 주소로 호스트의 서비스에도 닿을 수 있습니다. 파일에서만 격리될 뿐 네트워크에서는 격리되지 않습니다. 에이전트가 오프라인이어야 한다면 머신 앞에 방화벽을 두세요. snowpea는 이를 위한 플래그를 두지 않습니다.

## 샌드박스가 막아 주지 않는 것

- **프로젝트 디렉터리는 쓰기 가능합니다.** 에이전트는 `.git`, `.snowpea/`, `.claude/`를 포함해 그 안의 무엇이든 바꿀 수 있습니다. 에이전트가 쓴 것을 호스트에서 실행하기 전에 `git diff`와 훅·스크립트 파일을 확인하세요.
- **네트워크는 열려 있고**(위) 비밀 값은 읽을 수 있습니다(위).
- 가상 머신이 아니라 컨테이너이며 호스트의 커널을 공유합니다. 사고와 부주의한 에이전트를 막는 용도이지, 커널 취약점을 가진 작정한 공격자를 막는 용도가 아닙니다.

## 요구 사항과 한계

- 사용자가 실행할 수 있는 Docker Engine 또는 Docker Desktop(`docker info`가 동작해야 함). Linux와 macOS이며 Windows는 아직 지원하지 않습니다.
- 대화형 터미널 UI만 됩니다. `--docker`는 `-c`, 하위 명령, `--remote`와 함께 쓸 수 없습니다.
- 첨부하거나 언급한 경로는 컨테이너 안에서 읽히므로 프로젝트 디렉터리 아래에 있어야 합니다.
- 마이크와 스피커는 컨테이너에 연결되지 않아 음성 입력과 음성 응답은 쓸 수 없습니다.
- 안에서는 브라우저가 열리지 않으므로 MCP 서버의 브라우저 로그인(OAuth)을 샌드박스에서 끝낼 수 없습니다. 호스트에서 먼저 로그인하세요. 결과가 복사됩니다.
